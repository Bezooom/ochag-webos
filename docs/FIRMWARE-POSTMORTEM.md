# Механика прошивки webOS 4.x: почему установка и автозапуск ломаются (Firmware Post-Mortem)

## Введение

Задача звучит просто: поставить на root-нутый LG открытый лаунчер, торрент-сервер и плеер.
На практике каждая попытка упирается в один и тот же набор ошибок, которые в апстримах не описаны —
их README описывают **что** ставить, но не **почему это не ставится**:

- `Only absolute URLs are supported` — при попытке указать файл вместо URL;
- `Invalid file checksum (sha256:<hash> expected, got <hash>)` — при формально верном хеше;
- `Unknown method "install" for category "/dev"` — при включённом, казалось бы, Developer Mode;
- `-5: ipk verified failed` — при совпавшем размере и sha256;
- пустой вывод `luna-send-pub` и `Denied method call "getForegroundAppInfo"`;
- `"processId":""` при живом приложении на экране.

Ниже — что именно происходит внутри и какие обходы мы применяем. Все выводы получены на
**LG 43UN71006LB, webOS 4.5.0, HBC 0.6.3**; команды приведены в том виде, в котором их можно повторить.

## 1. Контракт установщика: `http(s)` и голый sha256

`com.webos.appInstallService` принимает пакет одним вызовом через сервис HBC:

```sh
luna-send -a webosbrew -n 30 luna://org.webosbrew.hbchannel.service/install \
  '{"ipkUrl":"<url>","ipkHash":"<hash>","subscribe":true}'
```

Механика: сервис **скачивает** файл по URL, считает sha256 потока и сверяет со строкой `ipkHash`.

- Локальный путь (`/tmp/app.ipk`) и `file:///tmp/app.ipk` отклоняются до скачивания — сервис валидирует
  схему URL: `Only absolute URLs are supported`.
- Сравнение хеша **строковое**: `"sha256:abcdef…"` в `ipkHash` даёт
  `Invalid file checksum (sha256:abcdef… expected, got abcdef…)`, то есть префикс попадает в ожидание,
  но не в факт. Лечение: голый hex.

Отсюда правило кита: `ipkHash = sha256sum | cut` без префиксов (`lib/hbc.sh:ipk_hash`).

## 2. Пропускная способность установщика: 1 КБ/с и локальный сервер

Замеры на одном и том же канале:

| Файл | Через установщик (LAN-HTTP) | Через `wget` на самом ТВ |
| :--- | :--- | :--- |
| OMP, 488 КБ | ~600 с (≈0.8 КБ/с) | <1 с |
| Hearth, 3.6 МБ | ~400 с | <1 с |

То есть узкое место — не Wi-Fi и не сервер раздачи, а **чтение и инкрементальный sha256 внутри
установщика**: он забирает поток мелкими порциями и публикует прогресс в подписку.

Обход: положить ipk **на сам ТВ** и отдать его локальным сервером на `127.0.0.1`. Тогда у установщика
исчезает сетевое плечо, и 23 МБ проходят за один прогон.

```sh
# на ТВ: статический сервер из /tmp на 127.0.0.1:8081 (node есть в прошивке, версия 8.12)
setsid node /tmp/_srv.js >/tmp/_srv.log 2>&1 &
# установка
luna-send -a webosbrew -n 100 luna://org.webosbrew.hbchannel.service/install \
  '{"ipkUrl":"http://127.0.0.1:8081/app.ipk","ipkHash":"<sha256>","subscribe":true}'
```

Кит делает это автоматически для пакетов крупнее 2 МиБ (`hc_install_ipk`, режим `tv`);
мелкие отправляет обычным HTTP с компьютера, потому что там разница несущественна.

## 3. Проверка подписи и граница ручной распаковки

`-5: ipk verified failed` приходит **после** скачивания и сверки хеша: это отдельная проверка
подписи пакета. Самодельный «тонкий» ipk (только `appinfo.json`, `services.json` и иконки,
собранный из `control.tar.gz` исходного пакета) тоже не проходит — подпись считается по архиву целиком.

Из этого следует граница, которую важно знать: **распаковка `data.tar.gz` руками** работает только
для приложения, которое **уже зарегистрировано** в базе установщика.

| Сценарий | Результат |
| :--- | :--- |
| распаковать поверх **установленного** приложения | работает, переживает перезагрузку (так обновлялся наш прежний лаунчер) |
| распаковать **новое** приложение | `launch → "not exist"`, сервисные методы → `Service does not exist`: роли регистрирует установщик |

Поэтому для `TorrServer` кит не притворяется установщиком, а берёт из пакета **бинарь** и запускает
его демоном: веб-морда `:8090` и API `/torrents` доступны полностью, пропадает только телевизионный GUI.

## 4. Сессия Developer Mode: `/dev/install`, ключ на `:9991` и враньё `ares-novacom`

Пока сессия Dev Mode жива, доступен `dev/install`. Когда она истекает, любой вызов — включая
`ares-install` — падает с `Unknown method "install" for category "/dev"`, хотя в приложении
Developer Mode по-прежнему написано «Enabled».

`ares-novacom --getkey` в этот момент рапортует `Failed to get ssh private key` — сообщение
не имеет отношения к ключу. Механика: getkey — это обычный `GET` с ключевого сервера
`http://<TV>:9991/webos_rsa`, а сервер живёт, только пока открыто приложение Developer Mode.
Проверка в одну строку:

```bash
nc -z -w2 <TV> 9991 && curl -s http://<TV>:9991/webos_rsa | head -3
```

Полученный файл — **зашифрованный PEM** (`Proc-Type: 4,ENCRYPTED`, `DEK-Info: AES-128-CBC`),
пароль к нему — те самые 6 цифр с экрана. Это же ключ нужен для SSH на порт `3000`;
`ssh-keygen -y -f` без пароля падает, и это не повреждение файла.

Вывод для эксплуатации: наличие root (HBC) делает Dev Mode необязательным — именно поэтому кит
ходит на `9922` через dropbear и HBC-сервис, а Dev Mode нужен только как аварийный вход.

## 5. TTY и права: почему luna молчит

Два независимых ограничения, которые выглядят как «сервис не отвечает»:

1. **`luna-send-pub` требует TTY.** Без `ssh -t`/`-tt` вывод пустой при коде возврата 0 —
   luna-send-pub привязывает вывод к терминалу. Кит всегда зовёт `tv_luna_ssh` с `-tt`.
2. **`prisoner` не имеет прав на часть методов.** `getForegroundAppInfo` отвечает
   `Denied method call … for category "/"`. Чтение переднего плана и всё, что касается системы,
   выполняется в root-сессии HBC:

```sh
luna-send -a webosbrew -n 1 luna://com.webos.applicationManager/getForegroundAppInfo '{}'
```

Сторож кнопки Home поэтому и работает как root-хук: из `prisoner` он бы просто не увидел, какой экран
впереди.

## 6. Кавычки, `/tmp` и порядок в init.d

- **Кавычки.** HBC `exec` принимает `{"command":"…"}`, и команда уезжает в `sh -c`. Любые одинарные
  кавычки внутри JSON рвут строку, а экранирование через три уровня оболочек превращается в лотерею.
  Кит пишет скрипт в `/tmp` и вызывает `sh /tmp/x.sh` — тело больше не участвует в разборе.
- **`/tmp`.** `prisoner` и root видят общий `/tmp` (так копируются хуки и ipk), но каталог живёт
  в памяти и чистится: файл, положенный в одной сессии, ко второй может исчезнуть. Отсюда правило
  «класть и использовать в одном шаге».
- **Порядок и блокировка.** `init.d`-хуки запускают долгоживущие процессы в фоне (`nohup`/`setsid`),
  иначе `startup.sh` ждёт их и загрузка ТВ растягивается. Именно поэтому `TorrServer` стартует
  через `setsid`, а хук сразу делает `exit 0`.
- **Задержка dropbear.** После перезагрузки SSH на `9922` поднимается не мгновенно (в нашем замере —
  минуты). «Нет ответа» сразу после ребута не означает «root потерян».

## 7. Состояние appMgr: пустой `processId` и зависание на `downgrade`

- `getForegroundAppInfo` может вернуть `"appId":"…","processId":""` — приложение **уже упало**,
  а appMgr держит запись о переднем плане. Проверять живость по `processId`, а не по `appId`.
- Переустановка **той же версии** уходит в ветку `"downgrade":true` и застревает на
  `state:"ipk parsing"`; ни ошибки, ни завершения. Лечение: поднять `version` в `appinfo.json`
  или (для уже зарегистрированного приложения) обновить файлы напрямую.
- `cp -a` поверх каталога работающего приложения может уронить сессию dropbear и увести ТВ
  в перезагрузку. Это не потеря данных: файлы на диске остаются, хуки возвращаются после старта.

## 8. Два способа подменить Home и почему они конфликтуют

| Способ | Механика | Плюс | Минус |
| :--- | :--- | :--- | :--- |
| **helper script** (Hearth, «Replace LG Home with a helper script») | сторож смотрит `getForegroundAppInfo` и открывает лаунчер, когда впереди `com.webos.app.home` | ничего не подменяет, обратимо одной галочкой | LG-экран успевает мигнуть |
| **script + SAM** | поверх каталога `com.webos.app.home` монтируется заглушка, SAM перезапускается один раз | LG Home не появляется вовсе | ломает настройку соотношения сторон; стартует поздно (~30 с) |
| **LG Input Hook** | перехват самой кнопки Home в сервисах пульта | без мигания, до отрисовки LG Home | нужен ID клавиши своего пульта |
| **наш `85-home-watch`** | root-сторож, как helper script, но наш | ставится скриптом, не зависит от версии Hearth | дублирует helper script, если включён он же |

Практический вывод: **Input Hook + один из сторожей** — минимум мигания и максимум устойчивости.
Если включён «script + SAM» (`/var/lib/webosbrew/init.d/47-launcher-takeover`), наш сторож становится
страховкой и его можно снять.

## Итог: симптом → причина → лечение

| Симптом | Причина | Лечение |
| :--- | :--- | :--- |
| `Only absolute URLs are supported` | установщик валидирует схему URL | отдавать ipk по `http://` |
| `Invalid file checksum (sha256:… expected, got …)` | строковое сравнение с префиксом | `ipkHash` = голый hex |
| установка идёт часами | инкрементальное чтение внутри установщика | сервер на `127.0.0.1` самого ТВ |
| `-5: ipk verified failed` | подпись пакета, а не хеш | только подписанные пакеты; иначе — бинарь демоном |
| `launch → not exist` после ручной распаковки | роли регистрирует установщик | ручная распаковка только поверх установленного |
| `Unknown method "install" for category "/dev"` | сессия Dev Mode истекла | root через HBC (9922), Dev Mode как аварийный вход |
| `Failed to get ssh private key` | закрыто приложение Dev Mode | открыть его, `/webos_rsa` на `:9991`, пароль — код с экрана |
| пустой вывод `luna-send-pub` | нет TTY | `ssh -tt` |
| `Denied method call "getForegroundAppInfo"` | права `prisoner` | вызов через root-сессию, `-a webosbrew` |
| зависание на `ipk parsing` | `downgrade:true` при той же версии | поднять версию |
| `"processId":""` | приложение упало | судить по `processId` |
| Home открывает LG-экран | нет перехвата клавиши | Input Hook (`keybinds.json`) + сторож |
